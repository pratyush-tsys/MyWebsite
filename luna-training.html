DAY 1

Module 1: HSM and Cryptography Fundamentals

Slide 1

Module 1 Learning Objectives

  • Understand the physical and logical security boundaries of the Luna Network HSM 7
  • .
  • Master the difference between hardware-based roots of trust and software-based keystores [Fundamentals Slide 5].
  • Define the role of HSMs in meeting regulatory standards like FIPS 140, Common Criteria, and eIDAS
  • .
  • Overview of the K7 Cryptographic Engine architecture [Fundamentals Slide 7].
Slide 2

What is an HSM?

  • A dedicated, tamper-resistant hardware device for cryptographic processing
  • .
  • Root of Trust: Provides a single, secure point of origin for all cryptographic keys in an organization.
  • Validation: FIPS 140-2 Level 3 validated, ensuring physical tamper evidence and logical separation of sensitive data [1, Fundamentals Slide 7].
Slide 3

Why Organisations Use HSMs

  • Regulatory Compliance: Meeting mandates like FIPS 140, PCI-DSS, and eIDAS
  • .
  • Separation of Duties: Enforces a model where appliance administrators cannot access cryptographic keys
  • .
  • Secure Key Lifecycle: Ensures keys are generated using a hardware-based Random Number Generator (RNG) and never exist in the clear outside the module [Fundamentals Slide 7].
Slide 4

Hardware Security Boundary: The K7 Engine

  • The Luna K7 Cryptographic Engine is the internal hardware module
  • .
  • It is physically and logically distinct from the host appliance and its general-purpose Linux OS
  • .
  • Design: Sensitive objects like private keys are never stored unencrypted within the module [Fundamentals Slide 7].
Slide 5

Protecting Keys at Rest (MTK and KEK)

  • Master Tamper Key (MTK): An internal hardware key that encrypts all internal data. It is destroyed instantly if physical intrusion or environmental excursions (over-temp/voltage) are detected
  • .
  • Key Encryption Key (KEK): A global key that wraps all user objects, partition structures, and cloning vectors
  • . It is deleted if the HSM is decommissioned
  • .
Slide 6

Cryptographic Math in Hardware

  • All math occurs in volatile working memory within the K7 engine.
  • Decrypted keys exist only for the duration of a session and "evaporate" if power is lost, preventing "cold boot" or memory scraping attacks common in software [Slide 6, 9].
Slide 7

Symmetric vs. Asymmetric Cryptography

  • Symmetric: Uses the same key for encryption and decryption (AES, DES, 3DES). AES-256 is the standard for high-performance data encryption
  • .
  • Asymmetric: Uses a public/private key pair (RSA, ECC).
  • Signatures: Support for RSA (up to 4096-bit) and ECC for digital signatures and non-repudiation [Fundamentals Slide 7].
Slide 8

Hashing and Digital Signatures

  • Hashing: Creates a unique message digest (MD5, SHA-1, SHA-2) for integrity [EFT Guide 66].
  • Signatures: Combining hashing with asymmetric keys to prove the origin of a message or file.
  • Luna 7 supports high-performance signing, often exceeding 600 RSA-2048 operations per second.
Slide 9

HSM vs. Software Keystore

  • Isolation: Software keystores share memory with the OS and other apps; Luna HSM provides a "Chinese Wall" between the appliance and the module
  • .
  • Extraction: In a software keystore, a compromised admin can copy the key file. In a Luna HSM, keys are marked always-sensitive and never-extractable
  • .
Slide 10

FIPS 140 Concepts and Approved Mode

  • HSM Policy 12: Controls FIPS 140 approved configuration. When OFF, the HSM only permits NIST-sanctioned algorithms
  • .
  • Remapping: RSA PKCS key generation is automatically remapped to FIPS 186-3/4 compliant methods [HSM Guide 46, Slide 35].
  • Self-Tests: The HSM performs extensive power-up self-tests to ensure firmware integrity.
Slide 11

Luna Network HSM Use Cases

  • PKI: Root-of-trust for internal or public Certificate Authorities.
  • Payments: Secure PIN management and ATM transaction processing (EFT functions) [66, EFT Guide].
  • Cloud: Partitioning allows "HSM-as-a-Service," where multiple clients share one appliance securely
  • .
DAY 1

Module 2: Luna HSM Architecture

Slide 12

Module 2 Learning Objectives

  • Visualize the layered Luna architecture (Appliance vs. HSM vs. Partition) [Fundamentals Slide 5].
  • Understand the administrative roles (SO, PSO, CO, CU) [Fundamentals Slide 11].
  • Differentiate between traditional (V0) and modern (V1) partitions
  • .
  • Explain Multifactor Quorum (PED) authentication and Cloning Domains
  • .
Slide 13

The Layered Architecture Model

  • Layer 1: The hardened physical appliance (Linux host, networking, power) [Fundamentals Slide 5].
  • Layer 2: The Luna K7 Cryptographic Engine (the "Vault") [1, Fundamentals Slide 5].
  • Layer 3: Logical Application Partitions (the "Safe Deposit Boxes") [Fundamentals Slide 5].
Slide 14

Appliance vs. HSM Concepts

  • Appliance Administration: Networking, users, logs, and updates. Executed in LunaSH
  • .
  • HSM Administration: Keys, partitions, policies, and crypto operations. Executed via the HSM SO or PSO roles
  • .
  • Independence: An appliance admin cannot see or use keys inside an HSM partition
  • .
Slide 15

HSM Hardware Components

  • Redundant Power: Dual hot-swappable power supplies [Appliance Guide].
  • Connectivity: 4x 1G Ethernet ports (eth0-eth3) with bonding support
  • .
  • Serial Port: RJ45 console for initial configuration [Appliance Slide 14].
  • USB Ports: Front and back ports for Luna PED connection [Fundamentals Slide 7].
Slide 16

HSM Partitions: The "Virtual HSM"

  • The HSM is divided into multiple independent containers called partitions
  • .
  • Each partition acts as its own virtual HSM with unique login credentials, policies, and key storage [Fundamentals Slide 5].
  • Administrative Partition: The global space owned by the HSM SO.
Slide 17

Partition Architecture: Version 0 (V0)

  • Traditional Model: "Keys Always in Hardware"
  • .
  • All objects are stored strictly in the internal memory of the HSM engine.
  • Compatibility: Designed for legacy applications that rely on standard cloning protocols
  • .
Slide 18

Partition Architecture: Version 1 (V1)

  • Modern Model: Supports Scalable Key Storage (SKS)
  • .
  • Allows for millions of keys by extracting them as encrypted blobs
  • .
  • Compliance: Required for eIDAS-compliant Per-Key Authorization (PKA)
  • .
Slide 19

Scalable Key Storage (SKS) and Master Keys

  • SKS Master Key (SMK): A unique symmetric key bound to a V1 partition that never leaves the HSM
  • .
  • Blobs: Keys are generated in hardware and extracted as secure AES-256-GCM encrypted blobs (up to 64KB)
  • .
  • Operational Flow: Blobs are stored in external databases and temporarily inserted into HSM volatile memory for use
  • .
Slide 20

HSM Security Officer (HSM SO)

  • Global Authority: The master administrator of the module
  • .
  • Tasks: Initializes the HSM, sets global security policies, and creates the partition containers
  • .
  • Authentication: Authenticates via the Blue HSM SO PED key
  • .
Slide 21

Partition Security Officer (PSO)

  • Partition Authority: The administrator of a specific application partition
  • .
  • Tasks: Initializes the partition roles (CO/CU) and sets partition-level policies
  • .
  • Authentication: Authenticates via a distinct Blue Partition SO PED key
  • .
Slide 22

Crypto Officer (CO) and Crypto User (CU)

  • Crypto Officer: Full operational control; can generate, use, and delete keys within their partition
  • .
  • Crypto User: Restricted read-only role; can sign or encrypt but cannot manage objects
  • .
  • Authentication: Authenticates via Black (CO) or Gray (CU) keys
  • .
Slide 23

Independent Role: The Auditor

  • Responsible for managing HSM security logs
  • .
  • Isolation: The Auditor has no access to cryptographic keys or any other HSM services
  • .
  • Authentication: Authenticates via the White Auditor PED key
  • .
Slide 24

Role Separation and Governance

  • Administrative roles (SO/PSO) perform provisioning
  • .
  • Operational roles (CO/CU) perform cryptography
  • .
  • The "recover" appliance user can access system logs but not HSM secrets
  • .
Slide 25

Authentication: Password vs. PED (Quorum)

  • Password: Uses alphanumeric strings (FIPS 140-2 Level 3 equivalent)
  • .
  • PED (Multifactor Quorum): Uses physical USB PED keys and a "Trusted Path" display
  • .
  • Security: PED authentication prevents secrets from ever appearing on a computer keyboard or screen
  • .
Slide 26

Luna PED Concepts and Hardware

  • Connects to appliance USB ports [Fundamentals Slide 7].
  • Modes: Local PED (physical connection) vs. Remote PED (network connection via Orange RPV key)
  • .
  • Secure display for M-of-N assembly and PIN entry [Fundamentals Slide 7].
Slide 27

Shared Secret PED Keys (M-of-N)

  • Concept: Splitting a role secret across multiple physical keys (N)
  • .
  • Quorum: A minimum number (M) must be present to authenticate (e.g., 3-of-5).
  • Benefit: Enforces Dual Control, preventing a single person from misusing the HSM.
Slide 28

Summary of PED Key Colors

  • Blue: SO/PSO Administrative Secrets
  • .
  • Red: Cloning Domain (Security boundary)
  • .
  • Black: Crypto Officer operational secret
  • .
  • White: Auditor role oversight
  • .
  • Orange: Remote PED Vector (RPV)
  • .
  • Purple: Secure Recovery Key (SRK) for Backup HSM
  • .
Slide 29

Domains and Cloning Domains

  • The Perimeter: A Cloning Domain (Red key) cryptographically defines which partitions can talk to each other
  • .
  • Requirement: Objects can only be cloned or moved if the source and target share the identical domain
  • .
  • Extended Domains: Firmware 7.8.0+ supports up to three domains per partition [Fundamentals Slide 12].
DAY 1

Module 3: Appliance Administration

Slide 30

Module 3 Learning Objectives

  • Verify hardware integrity and establish console access [8, Module 1 Plan].
  • Configure network interfaces, bonding, and DNS
  • .
  • Manage appliance users and hardened access via LunaSH
  • .
  • Administer time services (NTP) and appliance certificates
  • .
Slide 31

Physical Installation Considerations

  • Tamper Seals: Verify the two seals on the unit against Advanced Shipping Notifications. Check for "ALERT" markings [Module 1 Plan].
  • Power: Redundant power to independent circuits.
  • Airflow: Standard 19-inch rack mounting with front-to-back airflow.
Slide 32

Initial Appliance Access

  • Mandatory: First-time setup must be via a serial RJ45 connection [Appliance Slide 14, 8].
  • Settings: 115200 baud, 8 bits, No parity, 1 stop bit [Appliance Guide 8].
  • Login: Default appliance account is admin [Appliance Slide 14].
Slide 33

Hardened OS and Luna Shell (LunaSH)

  • The appliance runs a custom Linux kernel
  • .
  • Direct shell (root) access is disabled. All administration is through the LunaSH command set
  • .
  • Queueing: Commands are executed sequentially to protect module performance.
Slide 34

Appliance Users and Privileges

  • Admin: Full appliance management (networking, user management, service restarts)
  • .
  • Operator: Limited maintenance; cannot reset passwords or delete logs
  • .
  • Monitor: Read-only access to view appliance status and settings
  • .
Slide 35

Network Interface Configuration

  • Set static IP: network interface static -device eth0 -ip <IP> -netmask <Mask> -gateway <GW> [73, Appliance Artifact].
  • Support for 1G and 10G interfaces (eth0-eth3) [Appliance Slide 2].
  • IPv6 is supported with specific configuration constraints
  • .
Slide 36

Interface Bonding for Redundancy

  • Combine physical ports into a single logical bond0 (eth0/eth1) or bond1 (eth2/eth3)
  • .
  • Command: network interface bonding config -name bond0 -ip <IP> ...
  • .
  • Modes: Default is Mode 1 (Active-Backup); LACP (802.3ad) requires firmware 7.8.4+ and switch support
  • .
Slide 37

DNS and Service Binding

  • Add name servers: network dns add nameserver <IP> [72, Appliance Artifact].
  • Hardening: Use ntls bind or sysconf ssh to restrict traffic to specific physical or bonded interfaces
  • .
Slide 38

Time Governance: NTP

  • Critical for ensuring audit log timestamps and certificate validity are accurate
  • .
  • Add server: sysconf ntp addserver <IP> [77, Appliance Artifact].
  • Sync: sysconf ntp ntpdate <IP>
  • .
Slide 39

HSM Time Synchronization

  • Policy 57: Enabled in Firmware 7.8.0+, allows the HSM clock to automatically sync with the appliance every 24 hours [Policy 57 Note].
  • Prevents "clock drift" between the secure module and the logging host.
Slide 40

System Status and Health Checks

  • hsm show: Displays serial numbers, firmware version, and global policies
  • .
  • hsm status: Displays the current operational state (OK, Tamper, STM) [Hands-on Plan].
  • network show: Verifies current IP and DNS settings [72, Hands-on Plan].
Slide 41

Appliance Certificates (server.pem)

  • A unique certificate used for secure Network Trust Link (NTLS) client connections.
  • Command: sysconf regenCert creates a new identity for the appliance [10, 75, Appliance Artifact].
  • Supports RSA 4096-bit and ECC secp384r1.
Slide 42

SSH Security and Ciphers

  • Limit available ciphers: sysconf ssh ciphers set
  • .
  • Best practice: Regenerate fresh public keys for appliance access regularly
  • .
  • Mandatory use of secure MAC algorithms like hmac-sha2-512.
Slide 43

Firmware and License Management

  • Capabilities are factory-set (e.g., maximum partitions)
  • .
  • Licenses: Applied via sysconf license to unlock more partitions or Functionality Modules (FMs) [Appliance Guide 195, 37, 38].
Slide 44

Secure Transport Mode (STM)

  • Prevents man-in-the-middle attacks during shipment
  • .
  • Locked State: The HSM is unusable until a factory-provided Random User String and Verification String are entered
  • .
  • Recovered via the hsm stm recover command [Hands-on Plan].
DAY 1

Day 1 Hands-on: Lab Content

Slide 45

Lab Exercise 1: Connectivity

  • Goal: Establish physical console access.
  • Establishing the RJ45 Serial Connection.
  • Logging in as admin.
  • Executing user show to see default roles.
Slide 46

Lab Exercise 2: Network Setup

  • Goal: Place the appliance on the production network.
  • network interface static -device eth0 -ip 192.168.1.10 -netmask 255.255.255.0 -gateway 192.168.1.1.
  • network dns add nameserver 8.8.8.8.
  • sysconf ntp addserver 10.10.10.5.
Slide 47

Lab Exercise 3: Identity Generation

  • Goal: Create a unique identity for the unit.
  • sysconf regenCert.
  • Verification: ntls show to see the new certificate hash.
Slide 48

Lab Exercise 4: HSM Initialization (The "Hard Init")

  • Goal: Establish the root of trust and HSM SO role.
  • hsm init -label CorporateHSM.
  • Observation: The Luna PED will prompt for the Blue HSM SO key and the Red HSM Domain key.
Slide 49

Lab Exercise 5: Partition Provisioning

  • Goal: Create a container for client applications.
  • partition create -partition WebApp_Vault -version 0.
  • Observation: The HSM SO creates the "safe deposit box" but cannot see the "contents" within it.
